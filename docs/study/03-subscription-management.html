PortalとJobの実行構成

Portalの各機能がどこで動き、SQLやAPIMへどう接続するかを示します。

Portalは画面操作を受けてSQL・Graph・APIMを呼びます。SQL初期化Jobは配備時のDB準備、グループ観測Jobは15分ごとの組織確認を担当します。

実行リソースと接続先
構成要素役割と保守時の確認箇所
Portal / Container Appsca-${stem}-portal。常駐HTTP処理。接続設定と実行用IDはdeploy/application.bicep。
Azure SQLsqldb-${stem}-portal。公開接続を無効にして閉域接続し、実行用IDで認証。auth-database.tsとdeploy/database.bicepが担当。
APIMAPIMサブスクリプション管理はmanagement.azure.com、API試用は公開Gatewayへ要求する。通常のキー操作でAPIM全体を再配備しない。
Entra ID / Graphログインと、現在の所属・グループ属性を確認。所属照会はEntraアプリのClient IDとsecretで認証。
Key Vault / ACR / Log Analytics秘密情報、起動用イメージ、実行ログの保存先。ACRからの取得はSQLを経由しない。

Portalへの認証

Portalを利用する人を識別し、現在所属する組織と、会社・用途が登録されたAPIキーを対応付けるための機能です。

目的データ構造操作担当ファイル

認証とログイン状態の管理にはBetter Authを採用しています。Microsoft Entra IDで本人を確認し、Better AuthがSQLでセッションを管理します。

データ構造と保存先

データ持つ情報・関係
portalUser本人のレコード。EntraのテナントID＋Object IDで識別する。
portalAccount / portalSessionuserIdでUserを参照。AccountはMicrosoftアカウントとの対応、Sessionはセッショントークンと有効期限を持つ。
portalVerification認証途中の検証情報を期限付きで保存。OAuthトークンは保存しない。

操作の流れ

  1. Microsoftで本人を確認

    IDトークンを検証し、本人のテナントIDとObject IDを取得する。

  2. ログイン状態を保存

    User・Account・Sessionを登録し、以後はCookieとSQLセッションの期限を照合して本人を識別する。

  3. 管理できるキーへ対応付ける

    操作時にGraphで現在の所属グループを照会し、SQLに登録された所有グループ・製品承認・キー状態を照合する。キーに登録されたcompanyIdから利用会社を参照する。

本人とAPIキーを直接結ぶSQLの外部キーや、所属メンバー一覧を保存する表はありません。本人ID → Graphで現在所属を確認 → グループ所有のキー、という対応です。会社名だけで管理権限を与える実装ではありません。

担当ファイル

担当ファイル・フォルダ実装している処理と目的
components/login-panel.tsxMicrosoft認証の開始とログイン画面の表示。
app/api/auth/[...all]/route.tsサインインや認証の戻りを、認証用の受付処理へ渡す。
lib/auth-http.ts公開する認証操作、送信元、認証後の戻り先を検証する。
lib/auth-options.ts認証ライブラリBetter Authの設定と、保存前の処理をまとめる。
lib/auth-identity.tsMicrosoftのIDトークンを検証し、テナントと本人のIDを取り出す。OAuthトークンは保存前に除く。
lib/auth-session.tsCookieとSQLセッションを照合し、現在の本人をページやAPIへ渡す。
lib/auth-database.tsSQL接続プールと認証方法を設定する。Azureでは実行用IDで接続する。
lib/auth-schema.ts認証4表の対応と、セッションの有効期限を設定する。
lib/api-keys/graph.tsサインイン後の操作で、本人IDを使って現在の所属グループを確認する。
lib/api-keys/service.ts現在所属とSQLの所有グループ・製品承認を照合し、対象キーの操作を許可する。

APIキーの所有者はこの個人レコードではなく、後述するEntraグループです。

この機能の結果

本人をSQLセッションで識別し、操作時の現在所属から管理対象のAPIキーを判断します。

会社情報の登録

APIキーを利用する会社を登録し、利用料を実際に便益を受ける会社へ帰属させるための機能です。

目的データ構造操作担当ファイル

グループ会社間で利用の便益と費用負担がずれないよう、受益者負担に沿った配賦・請求に必要な対応情報を持たせます。利用量の集計、金額の算定、請求処理そのものは、この会社登録機能では行いません。

データ構造と保存先

データ持つ情報・関係
portalCompany会社ID・会社名・選択可能状態を保存。キー台帳のcompanyIdから参照する。
portalCompanyAudit会社名・選択可能状態の変更前後、操作者、日時を記録する。

操作の流れ

  1. 会社を登録する

    基盤管理者が会社名を入力し、重複を確認してportalCompanyへ有効な会社を登録する。会社の作成履歴も同時に保存する。

  2. 払い出し画面へ候補を返す

    有効な会社だけを会社選択肢として返す。APIキー払い出し時にcompanyIdで参照する。

  3. 名称や選択可否を変更する

    読込時の更新日時と現在値を比較し、会社情報と変更前後の監査を同じSQL処理で保存する。選択停止後も既存キーの会社参照は保持する。

会社名の変更は、この機能ではSQLへ保存します。通常のAPIMサブスクリプションのAPIM表示名との差分は、APIMサブスクリプション同期機能で反映します。

担当ファイル

担当ファイル・フォルダ実装している処理と目的
components/company-administration/dashboard.tsx会社一覧と登録・変更の画面。
lib/company-administration/contracts.ts会社名、有効状態、更新時点の情報などの入出力を定義する。
lib/company-administration/http.ts会社管理APIの本人・入力・メソッドを確認する。
lib/company-administration/service.ts管理グループへの現在所属を確認し、会社一覧・登録・変更を指示する。
lib/company-administration/repository.ts会社名の重複、更新競合、CompanyとCompanyAuditの同時保存を扱う。
この機能の結果

登録した有効な会社が、APIキー払い出し時の選択肢になります。

APIキーの払い出し

Gatewayを利用するAPIキーを発行し、所有グループ・会社・利用属性をSQL台帳へ登録する機能です。

目的データ構造操作担当ファイル

サインイン後、利用者はAPIキー管理から会社・所有グループ・用途などを指定します。所有者は個人ではなくEntraグループです。現在のメンバーが管理し、担当者の退職後も引き継げます。

APIMではAPIのまとまりを「製品」、その利用許可を「APIMサブスクリプション」として管理します。通常の払い出しは、リリース済みAPIを束ねたreleased-apis製品へ固定します。

データ構造と保存先

テーブル保存する目的
portalApiKeyGroupキーを所有するEntraグループの承認と、Graphで観測した状態。
portalApiKeyProduct所有グループごとの製品承認と、発行できるAPIMサブスクリプション数の上限。
portalApiKey用途・会社・所有・APIMサブスクリプションID・状態・棚卸し記録を保持する台帳。
portalCompanyキー発行時に選ぶ会社の分類。
portalApiKeyAudit発行・表示・停止・再開・棚卸し・削除の操作履歴。

portalApiKeyは、内部の台帳IDと実APIMサブスクリプションIDを分けて持ちます。所有グループ・製品承認・会社を参照し、同じ依頼を識別する依頼IDと状態を保存します。

発行時に登録する情報保存する意味
所有グループ・会社誰が管理し、どの会社の利用として費用を帰属させるか。
用途名・クライアント種別何のために、どの種類の利用元から使うか。
システム名・チーム名・連絡先棚卸しや問い合わせ時に、対象と担当先を確認するための属性。

操作の流れ

  1. 入力と許可の確認

    本人と入力を検証し、Graphの現在所属、有効会社、製品承認を確認する。

  2. SQLへ作成中の行を保存

    同じ依頼の重複と発行枠を確認し、SQLへcreating状態の予約を確定する。

  3. APIMサブスクリプションを作成

    同じAPIMサブスクリプションへの操作をロックし、APIMをGETで確認。不在ならPUTで製品・会社名・状態を指定して作成する。

  4. SQLを利用可能に更新

    APIMの結果を照合し、台帳をactiveへ更新して発行監査を記録する。

SQLとAPIMを分けて考える理由

SQLの取消では、成功済みのAPIM操作は戻りません。APIM作成後にSQL確定が失敗しても、予約の同じIDでAPIMを再照会して続行します。同じ入力の再試行には同じ依頼IDを使います。

キーの主・副キーはAPIMが生成・保持します。SQLにはキー実値を保存せず、発行応答にも含めません。キー表示やAPI試用など、必要な処理でAPIMから取得します。

APIMで確認する設定

設定対応する実装・確認内容
製品：released-apisapi-publication.bicep。API定義のreleased設定で、製品へ含めるAPIを決める。製品のpublished状態とAPIのリリース設定は別の項目。

APIMの管理操作はAzure Resource Manager（ARM）上のREST APIです。Portal実行用IDを使い、対象APIMを固定して呼びます。ロールは対象APIM単体ですが、APIMサブスクリプション以外も変更できる権限を含みます。

データ構造と保存先

データ持つ情報・関係

APIの試用

払い出したキーのうち、現在の本人が利用できるAPIMサブスクリプションを選び、Model / Tool GatewayのAPIを実行する機能です。

目的データ構造操作担当ファイル

データ構造と保存先

データ持つ情報・関係
SQLのAPIMサブスクリプション台帳画面が選ぶportalApiKey.idと、実APIMサブスクリプションへのapimSubscriptionId。所有グループ・製品・会社・状態は前のキー管理と共通。
画面からの実行要求台帳IDとサービスの入力を送る。キー実値をブラウザーから指定させない。
実行用の主キー・結果APIMから得た主キーはサーバー内で使用。入力・結果・キー実値を保存するPortal SQL表はない。

ここで使う所有グループ・製品承認・会社・台帳は、キー払い出しと同じデータです。台帳ID、実APIMサブスクリプションID、秘密キーはそれぞれ別の値です。

操作の流れ

  1. 候補を表示

    Graph所属とSQLの承認・台帳、APIMの製品内APIを照合する。必要なグループ登録・観測を保存する。

  2. 実行前に再確認

    台帳IDで対象をロックし、現在所属・承認・SQLとAPIMの状態を再確認する。

  3. キー取得と実行

    ARMで実APIMサブスクリプションと製品内APIを確認して主キーを取得し、各サービスの固定Gatewayへ送る。

サービスごとの要求・応答

  1. 入力を確認

    サービスごとに形式・容量・モデルの条件を検証して要求を組み立てる。

  2. 許可確認と送信

    共通のAPIMサブスクリプション確認を通り、固定されたGatewayのパスへ送信する。

  3. 結果を表示

    各サービスに合わせてJSON・ストリーム・ファイルを読み、検証した結果を画面へ返す。

担当ファイル

担当ファイル・フォルダ実装している処理と目的
lib/model-key-access.tsModel・PII・文書・MCPの試用で選べるAPIMサブスクリプション候補を返すHTTP処理。
lib/api-keys/service.ts候補の絞込みと実行前の権限確認。台帳IDから実APIMサブスクリプションIDと主キーを解決する。
lib/api-keys/repository.tsAPIMサブスクリプション台帳・承認・会社を読み、対象のロックとグループ観測の保存を行う。
