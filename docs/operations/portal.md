# Portalを修正・更新・切り戻す

[共通手順](common.md) · [運用テスト](../testing/operations-tests.md)

対象は既存Portalの画面・文言・ガイド・入力や結果表示の修正である。新しい管理機能やDB変更を、この手順の試験のために追加しない。手順の机上確認と、実環境への更新・受入は別に記録する。

## 1. 変更対象と復旧先を決める

1. 共通手順で同じ環境のparams・state・Tenant・Subscription・APIM識別子を確認する。別の構築・更新・撤去が実行中なら開始しない。
2. 対象画面、変更前後の表示、利用者ロール、合否を判断する入力・期待結果を一つに絞る。例えば既存の説明文を一か所変更し、同じ画面から代表APIを一度試す。
3. 変更前のソースrevision、稼働中のPortalイメージdigest・revision、対象画面と確認用データを保護した作業記録へ保存する。切戻し先イメージがACRに残っていることも確認する。
4. API契約・認証・DB・キー・署名鍵・環境設定を変更しない試験条件を選ぶ。これらも変える必要がある改修は、影響と復旧方法を別に確定してから実施する。

## 2. 対象を修正してローカルで確認する

| 修正するもの | 主な確認先 |
| --- | --- |
| 画面・入力・結果表示 | `apps/portal/components/`、`apps/portal/app/` |
| 日本語・英語の文言 | `apps/portal/lib/i18n/`と表示側コンポーネント |
| APIガイド・コード例 | 対象画面が読み込むガイド・例の正本とAPI契約 |
| BFFの入力検証を伴う変更 | 対象の`apps/portal/app/api/`と`apps/portal/lib/` |

1. 対象文字列やコンポーネントを検索し、対応する日本語・英語と必要な説明だけを修正する。APIフィールド名・内部識別子を表示文言の一括置換で変えない。
2. 既存の依存と必要なローカル設定を準備する。実情報をアプリ配下の`.env`やソースへ置かず、既存のローカル検証手順に従う。
3. `apps/portal`で次を実行する。失敗したら配備へ進まず、対象の修正または前提不足を解消する。

```sh
npm run lint
npm test
npm run build
```

4. 対象画面だけを表示し、変更した文言・入力・結果と対象ロールを確認する。今回の変更に関係するエラー・キャンセルも確認し、全画面・全端末の再試験へ広げない。
5. `git diff`で目的外のファイル・migration・設定変更が混ざっていないことを確認する。ここまでのローカル成功を実環境の成功とは扱わない。

## 3. 既存の個別配備で計画・実行する

リポジトリルートで、共通手順で選択した保護入力を使用する。

```sh
python3 -B scripts/operations/release.py --config "$DEPLOY_PARAMS_FILE" --component portal
```

1. 計画の対象アプリ・DB・ビルド／再利用・工程を確認する。これは資源ごとの完全なARM差分表示ではない。
2. このラッパーは既存のPortal個別配備を使い、イメージ作成だけでなくDB初期化・権限・APIM連携・WAF等も照合する。UIだけの専用配備や、これらを省略するモードがあると扱わない。予定外の差分があれば止める。
3. ソースと入力を変えず、同じコマンドに`--execute`を付けて実行する。構築後の更新に`azd up`・`azd provision`は使わない。

```sh
python3 -B scripts/operations/release.py --config "$DEPLOY_PARAMS_FILE" --component portal --execute
```

4. 今回の終了コードと、同じ環境の`state/portal-deployment.json`を確認する。過去の成功JSONだけで判断しない。SQL初期化失敗等で停止した場合、後続のアプリ更新も成功したと扱わない。

## 4. 更新後を受け入れる

1. 稼働digest・revisionが今回の配備結果と一致し、公開ヘルスが正常であることを確認する。
2. 正規ログインで対象画面を開き、変更前後の期待と表示を照合する。API試用を含めた場合は、正常認証の実応答と画面結果を確認する。匿名401やヘルス200だけを業務成功にしない。
3. 代表の既存導線を一つ確認し、今回対象外のAPI定義・Foundry配備・既存キー・DBデータ・権限が目的外に変わっていないことを変更前記録と照合する。キー値・Cookie・トークンを表示して照合しない。
4. 検証用入力と一時権限を回収し、変更内容、実結果、所要時間、保護した証跡保存先、残件を記録する。

## 5. 異常時は止めてから切り戻す

運用試験の異常条件は、ローカルの隔離した作業コピーで型・構文等の不正を一つ作り、上記の検査が失敗して配備前に止まることを確認する。故障箇所を戻して再検査し、不正ソースを`--execute`で配備しない。実SQLの権限破壊や本番データ変更を、この停止試験の代わりに行わない。

実配備が失敗・応答不明になった場合は、配備記録、アプリrevision、SQL初期化ジョブ等を対象限定で読み、成功済み・実行中・失敗を区別する。直ちに同じ更新を重ねない。

切戻しは確認済み旧digestを使う。現在のソース・テンプレート・paramsにも目的外変更がなく、DB・設定が旧アプリと互換であることを確認してから計画する。

```sh
python3 -B scripts/operations/release.py --config "$DEPLOY_PARAMS_FILE" --component portal --image-digest '<PORTAL_IMAGE_DIGEST>'
python3 -B scripts/operations/release.py --config "$DEPLOY_PARAMS_FILE" --component portal --image-digest '<PORTAL_IMAGE_DIGEST>' --execute
```

`<PORTAL_IMAGE_DIGEST>`は確認済みの`sha256:`形式を指定する。これはビルドを省略する指定であり、DB・権限・WAFの照合を省略する指定ではない。旧digestの稼働、対象表示、認証と代表API、対象外データの保持を確認して復旧を終える。DB互換性が確認できない場合は、旧イメージを強行せず復旧方法を確定する。
