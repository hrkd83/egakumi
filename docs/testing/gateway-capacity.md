# 3万人のAI Gateway容量計画と負荷試験

本文監査を追加したAI Gatewayの暫定性能目標。日々3万人がCodexやClaude Codeなどを使う想定とし、呼び出し頻度、集中度、接続時間、本文サイズは初期試算の仮定を置く。構成や数量は、利用の計測とAzureでの通し試験を経て決める。

配備するSKU、初期ユニット数、環境ごとの受入範囲は[prod・stg・devの容量設計](../reference/configuration/environment-capacity.md)を参照する。

## 1日あたりの利用からピークを求める

エージェントは、利用者の1回の指示からモデルを複数回呼び出す。推論の繰り返し、並行実行、再試行を含め、Gatewayに到達したモデルAPI呼び出しを数える。例えば、1人がエージェントを1日計2時間動かし、平均1分間に1回呼び出すと120回になる。端末内で完結する処理はこの件数に含めない。

- 3万人が1日に利用し、主な利用が10時間に集中する。ピーク時の呼び出しはその時間内の平均の4倍と仮定する。
- 別途Gatewayを通るツール等の通常HTTPは、モデル呼び出し件数の25%と仮定する。ツールのストリーミングの割合と接続時間は計測して加える。
- 接続数の試算ではモデル呼び出しを全件SSEとし、要求開始から応答完了までの平均を30秒と仮定する。

| 想定 | モデル呼び出し/人日 | モデル呼び出し/日 | ピーク時の開始数/秒 | ピーク付近の同時SSE |
| --- | ---: | ---: | ---: | ---: |
| 初回の負荷試験 | 60 | 180万 | 250（モデル200、その他50） | 6,000 |
| **本番の通常ピーク目標** | **120** | **360万** | **500（モデル400、その他100）** | **12,000** |
| 2倍のストレス試験 | 240 | 720万 | 1,000（モデル800、その他200） | 24,000 |

例えば通常ピークのモデル要求は、`30,000 × 120 ÷ (10 × 3,600) × 4 = 400件/秒`。ピークが持続する場合、同時SSEは `開始数/秒 × 平均接続秒数` で、`400 × 30 = 12,000本`。同じ500 RPSでも平均接続が60秒に伸びれば24,000本になる。短い集中、長時間の応答、再接続では、開始数と同時接続数をそれぞれ計測する。

## 監査転送と保管の目安

監査対象の平均本文をモデルは要求32 KiB・応答8 KiB、その他は要求4 KiB・応答4 KiBと仮定する。SSEの応答は完了までのイベント本文の合計。バイナリの原本は算入せず、SSEのイベント数、付帯情報、検査結果の大きさは別途測る。監査側が処理するのはキャッシュ適用前のAPI本文なので、モデル側のキャッシュヒット率でこの量を差し引かない。

| 指標 | 試算 |
| --- | ---: |
| 通常ピークの本文 | 約17.2 MB/s（`400 × 40 KiB + 100 × 8 KiB`） |
| Event Hubsの受信試験 | 約23 MB/s、2倍時は約45 MB/s（本文に30%の仮の余裕を加えて切り上げ） |
| 通常想定の本文 | 約155 GB/日（モデル360万件、その他90万件） |
| WORMの保持期間全体 | 約396 TB（毎日同量を2,557日保存した場合の圧縮前の本文） |

保存量には既存の診断ログ、監査レコードの付帯情報、インデックス、Storageの冗長化を含めていない。例えばモデルの平均本文が4倍の160 KiBなら、同じ件数でも約597 GB/日、2,557日で約1.53 PBになる。コードやツール結果の再送も想定し、平均付近とp95の本文サイズを含む分布で試験する。Event Hubs Premiumの公式例では、1 PUの受信は構成によって約5〜10 MB/s。例えば12,000接続が毎秒5イベント流し、1イベントを1監査レコードにすると、SSE応答だけで毎秒60,000レコードになる。イベント数、パーティションの偏り、保存・検査側の読み出しを観測し、連番を保つ集約単位と必要なPU数を決める。 [Event Hubsの処理能力とパーティション](https://learn.microsoft.com/en-us/azure/event-hubs/event-hubs-scalability)

## Azureでの受入目標

同じTLS設定・合成API応答・要求構成で、現行経路と中継を追加した経路を計測する。負荷生成側が設定したRPSを実際に送れたことを確認し、送信、開始、正常完了、意図した切断、429、5xx、タイムアウトを数える。通常HTTPとSSEを混在させる。

| 試験 | 暫定合格条件 |
| --- | --- |
| 通常ピークを60分 | 500 RPSと同時12,000 SSEを維持。正常完了率99.9%以上（意図的なキャンセルを除く）。現行経路に対するp95の追加遅延は通常HTTPの応答完了で50 ms以内、SSEの最初のイベントで100 ms以内 |
| 2倍を15分・接続時間の延長 | 1,000 RPS・同時24,000 SSEと、500 RPS・平均60秒で同時24,000 SSEを別々に試験。通常ピークと同じ応答・監査基準で余力を測る |
| 長時間SSE | 標準HTTPS 443の経路で、イベントが継続する240秒超と15分の応答を完走。イベント間隔、最初のイベント、途中の無通信区間、終了時の切断を確認する。無通信の許容時間は使用するモデルの実測と合わせて決める |
| 監査の照合 | 正常時は相関ID、連番、合成本文のハッシュでBlobまで照合し、説明できない欠損や重複を0件とする。圧縮や分割がある場合も復元して照合する |
| スケール・更新・障害 | 通常ピークで中継1レプリカ停止・リビジョン更新を試験。Event Hubsが受理したデータは保存停止からの復旧後に照合し、受理前の欠損は通知できることを確認する。検査サービスの停止も別途注入し、業務応答への影響と監査の遅延・欠損を計測する |

HTTP完了時間、SSEの最初のイベントと以降のイベント間隔はp50・p95・p99を記録する。WebSocketはアップグレード、同時接続、切断・再接続を別試験で測る。長時間SSEを試す際は、App Gateway、Firewall、ACA、YARP、APIMを含めて切断地点を特定する。ACAの標準HTTP ingressは公式記載が240秒で、APIMの `forward-request` の `timeout` はバックエンドから応答ヘッダーが来るまでの待機時間。SSEの継続中と開始前の待ち時間を分けて確認する。 [ACA ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview) · [APIMの転送ポリシー](https://learn.microsoft.com/en-us/azure/api-management/forward-request-policy)

## 容量の確定

- **ACAとYARP**。単一レプリカから始め、CPU、メモリ、送受信バイト数、同時接続、負荷分散の偏り、起動と終了時の接続処理を測る。Azureの通し試験で標準HTTPS ingressの処理能力を確認して、普段確保するレプリカ数と最大数を決める。
- **App Gateway、Firewall、APIM**。現行経路と中継経路を比べ、どの区間が先に飽和するかを確認する。本番公開例はAPIM Classic Premium 12ユニット。単一のFoundryホストにHTTP/1.1で転送し、全SSEが同時にバックエンド接続を占有する場合、公式上限は接続先あたり2,048本/ユニットなので、12,000本で6ユニット、24,000本で12ユニットが理論下限になる。接続先ごとの内訳、短いHTTP、ユニット間の偏り、停止時の縮退を加味して実測する。 [容量の入力項目](../reference/configuration/parameters.md#環境ごとに確定する容量) · [APIMの実行時上限](https://learn.microsoft.com/en-us/azure/api-management/api-management-gateways-overview#gateway-runtime-limits)
- **Foundry**。Gateway自体は合成バックエンドで計測する。モデルの供給能力は、試験するサブスクリプションの承認済みクォータから必要な容量を割り当て、配備単位で別に確かめる。通常ピークの400モデルRPSは24,000 RPM。仮に1回あたり入力8,000・出力1,000トークンなら、合算で入力1億9,200万 TPM、出力2,400万 TPM相当。モデルごとの利用割合と、キャッシュを含むクォータの数え方で見直す。 [配備容量の変更手順](../operations/foundry.md#容量だけを変更する) · [Azure OpenAIのクォータ](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota) · [FoundryのClaudeのクォータ](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/claude-models-quotas-limits)
- **監査経路**。キューの滞留量、Event Hubsの受理・制限、保存までの遅延、再処理、検査結果の着信を計測する。第三者製品の検査能力は合成入力で個別に測り、非同期処理が追いつくかを確認する。

先行利用で、1人日あたりのモデル・ツール呼び出し数、秒・分単位のピーク、同時SSE、応答時間、本文サイズ、再試行、クライアントごとの接続方式を集計する。計測値で仮定を更新し、Azureの通し試験に合格した構成を展開時の容量として採用する。 [現行の利用量観測](subscription-limits.md)
