# 構築資材・構築テスト仕様書

構築用資材と公開手順を使って、端末・Entra・DNS・構築入力の事前準備、入力検証、新規構築、個別配備・再配備、構成変更、証明書の発行・更新・復旧、SQL初期化、API公開、撤去が期待どおり完了することを確認します。資材で指定した資源・権限・保護設定と構築結果の一致も対象です。構築済み環境での業務API、認可、接続、ログ・監視の動作は [動作テスト仕様書](integration-tests.md)で管理します。

開発・テストの共通ルールと実行方法は [DEVELOPMENT.md](../../DEVELOPMENT.md)、公開の構築手順は [README.md](../../README.md)、構築入力は [params/](../../params/)、資材は [azure.yaml](../../azure.yaml)・[infra/](../../infra/)・[配備スクリプト](../../scripts/README.md)を参照してください。

## 1. 実施の段階と開始条件

公開手順の事前準備も試験対象とし、`PRE`項目は動作テスト完了やCore構築を待たず、独立した試行として開始できます。準備済みの外部資源を再利用する場合も、今回の資材・対象環境に対応することを確認し、他環境・他revisionの判定を転記しません。事前準備の合格と、Coreの有料設備の構築・撤去の合格は分けます。

Coreの新規構築・撤去は、次の開始条件を満たしてから実施します。

1. 判明済みの不具合を資材へ反映し、新規構築前に実行できるローカル検証を完了する。既存環境がある場合は、そこで実施できた動作確認も記録する。
2. 構築済み環境が必要な残件・個別再配備・修正後の再試験は、項目ID・期待結果・実施順序を計画へ明記し、構築後に確認する。未確認・不合格・再試験待ちを完了扱いにせず、未採用構成や利用者指定による対象外は理由を記録する。
3. 改修済み資材のGit revision、params参照・非秘密の設定hash、対象構成を固定する。
4. **その資材を使って構築し、本書の構築テストを新しい試行IDで実施する。** 公開手順の前提からの再現性と、構築後の残件・統合テスト・撤去を確認し、既存環境の状態や過去の配備成功だけで合格にしない。

事前準備の開始はCoreの再構築や既存環境の撤去を意味しません。再構築先・既存環境の撤去要否・費用・保持と切戻し条件はCoreの構築試行の開始前に記録します。

## 2. 実施方法と記録

開始前の本書と事前準備・構築試行の証跡は、`.local/<environment>/evidence/<run-id>/`へ保護保存します。[共通ルール](../../AGENTS.md)に従い、実params・秘密・state・証跡を同じ環境の領域内で分け、`.azure/`はazd専用として使います。本書の結果欄には、依頼者の指定により、今回までの判定と確認範囲・残件を環境非依存の要約として記録します。実値・試行の識別子・原本証跡の参照先・実設定から導出したhashは公開版へ持ち込みません。他環境・他revisionとは非公開の結果票・証跡を分け、新しい試行へ過去の合格を転記しません。未採用構成は理由を記録して対象外にします。事前準備とCore構築を別試行にする場合は、準備した資源の対象・確認日時を非公開記録で引き継ぎ、構築直前に一致を再確認します。

### 2.2 適用条件・副作用・判定

- 各行の「全構成」は、選択した同一params・azd環境・Azure Subscriptionを使う場合に適用します。test／productionという環境名だけで保護設定を切り替えません。
- `[読取]`は現物・記録・設定の確認、`[ローカル更新]`は試験用設定や計画ファイルの作成、`[更新]`はAzure・DNS等の変更、`[課金]`は資源作成・API利用等の費用発生、`[停止]`は通信や業務を中断し得る操作、`[削除]`は回収不能なデータ消失を含み得る操作です。複数の印がある場合はすべて該当します。
- `[更新]`以降の試験は、対象・費用・保持・切戻し条件を合意した隔離検証環境で実施します。`[削除試行]`も削除要求を実際に送る試験なので同じ管理が必要です。異常注入は実利用中の環境へ行わず、正常設定を保存してから一条件ずつ変更し、試験後に復元します。Locked WORMやpurge protectionの解除を試験の前提にしません。
- 企業ハブ、native gRPC、Premium IDPS、ログアラートなどは、行に示した機能を採用した構成だけへ適用します。証明書はAzure Public DNSとUAMIによるDNS-01を対象とします。対象外の根拠を記録し、未確認条件を先に合格へ変更しません。
- 証跡には実行時刻、revision、paramsの参照と非秘密ハッシュ、資源ID、HTTP状態、追跡ID、保護したログへの参照を記録します。鍵、token、証明書の秘密部分、パスワード、署名URL、利用者の実データは貼り付けません。構築成功、公開疎通、運用監視、撤去完了をそれぞれ実測します。
- 画面エビデンスは、作業で作成・変更して保存した設定画面だけを取得します。アプリ内ブラウザーの表示領域を1920×1080ピクセルにし、ページ全体の縦長画像にせず、保存した画像の実寸も確認します。サインイン・MFA・認証コード・secretの値が表示される画面や、無関係な画面、確認のために開いただけの画面は撮影しません。撮影のために設定を変更しません。
- 画像・CLIや読取APIの確認結果・設定表・試験用ユーザー等の対応表は、アクセスを制限した`.local/<environment>/evidence/`で管理します。設定画面の証跡と読取結果を区別し、Git管理する資材・公開文書・配布物へコピー・リンク・同梱しません。

判定は`PASS`、`FAIL・調査中`、`FAIL・修正中`、`再試験待ち`、`一部確認`、`条件不足`、`未実施`、`対象外`を使います。資材を修正しただけではPASSにせず、固定したrevisionで手順と全期待条件を実測して判定します。構築した環境での疎通・動作確認も新しい試行として記録し、旧環境の合格を転記しません。

推奨順は、公開手順による事前準備・新規clone・入力検証・対象照合 → 容量・前提検査 → 基盤と証明書 → Gateway・SQL・API公開 → Portal → 構築結果の照合・新環境の疎通確認 → 更新・異常時の再開と復旧 → 撤去・残存確認です。異常注入・更新・撤去は正常系と対象を分け、停止・削除前に前提と証跡を保存します。

人が公開手順を順に実行した結果で判定します。手順にない臨時コマンド、Codexによる入力の補完、Azureへの直接修正が必要になった条件はPASSにしません。不足を正式資材・公開手順へ反映し、改訂した手順で再試験します。既存資源の照合・再利用だけで新規作成の再現性を確認したとは扱いません。
