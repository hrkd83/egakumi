# 運用テスト仕様書

[運用手順](../operations/README.md) · [構築・統合テスト](README.md)

運用中にPortal、APIMのAPI定義・ポリシー、Foundryモデルを変更する手順を確認する。3業務の正常反映・失敗時の停止・復旧各1件と、共通確認3件の**計12件**に絞る。新しい管理機能の開発や、構築・統合テスト全項目の再実行は含めない。

## 実施前の準備

1. 初期構築済みの専用検証環境を使う。初期構築が必要なら[構築手順](../setup/06-deploy.md)で1回作成し、正常なGateway・Portalを確認してから運用テストへ入る。運用更新のために`azd up`・`azd provision`を再実行しない。
2. [共通手順](../operations/common.md)でコミット、params・参照config、APIM識別子、Core state、認証先、現物の対象を照合する。同じ環境を並行更新しない。
3. 変更前のPortal／Brokerのソース・digest、API定義・ポリシー、モデルの配備名・版・SKU・容量を保護保存する。旧イメージが現在のDBと互換であることを確認する。
4. 正常要求に使う専用キーと一般利用者のPortalログインを用意する。Azure・Foundryの変更は権限を持つ運用担当者が行う。パスワード・MFAが必要なら試験開始前に本人操作の時間を確保する。
5. 代表モデル1つと、正常・拒否に使う短い合成入力を決める。追加モデルや版・容量の利用可否は先に確認し、利用枠を確保できない変更を試験中に探し続けない。
6. 下表の変更例を今回のソースへ対応付け、変更内容・刺激・期待値・戻す値を実施票へ固定する。実環境値・秘密・実測記録は`.local/<environment>/`に保存する。

### 代表的な変更と観測

| 業務 | 変更例 | 反映と確認 | 元へ戻す方法 |
| --- | --- | --- | --- |
| Portal | 既存画面の説明文を1か所変更する。API・DB・認証契約は変えない | 対象のローカル検査→Pの計画→実行。対象画面の新文言、公開ヘルス、既存APIの利用を確認 | 旧ソース・互換性確認済みの旧digestでPを計画・実行。旧表示と既存利用を確認 |
| APIM | 既存APIの入力サイズ上限等、定義で表現できる制約を1つ変更する | ローカル検査→Gの計画→実行。実API・生成ポリシーと、認証付き正常要求・境界超過・未認証要求を確認 | 定義を旧値へ戻してGを再実行し、旧制約と既存APIを確認 |
| Foundry | 既存の代表配備の容量を、小さい確保可能な増分だけ変更する | Foundry GUIで変更→実配備に参照config正本の照合値を合わせる。容量だけならG／Pは不要。実容量と、同じGateway・Portalの代表要求を確認 | GUIで旧容量へ戻し、参照configも旧値へ戻す。実配備と設定の一致を確認 |

P／Gは[共通手順の個別配備](../operations/common.md#計画してから個別に反映する)を指す。APIのprofile別上限がある場合は、今回使うprofileと適用値を固定する。Foundry配備の変更だけでAPIの許可やPortalの表示が変わるとは扱わない。

## 実施順と効率化

1. 共通確認と3業務のローカル異常系を先にまとめて実施する。不具合を一覧化して同系統ごとに修正し、配備前に再検査する。
2. Foundryの容量を先に変更し、参照configの照合値を実物へ合わせる。続いて正常候補のAPI上限とPortal文言を、G→Pの1組で反映する。実配備・正常・拒否を各IDへ対応付けて確認する。
3. 容量・参照config・API定義・Portalソースを変更前へ戻し、復旧用のG→旧digest指定Pの1組で反映する。各業務のために基盤を作り直さず、3つの復旧IDを同じ復旧作業で確認する。反映中は独立した記録・読取確認を進める。
4. 最終正常・拒否と試験対象の回収を確認し、IDごとの結果を記録する。環境全体の撤去は、結果確認と合意後に[正式な撤去手順](../operations.md#撤去する)で行う。

応答不明の場合は同じ操作を重ねず、配備・ジョブ・現物を読み、実行中・完了・失敗を区別して同じ入力から再開する。正常系を妨げる不具合と、独立して続けられる項目を分ける。

## 所要時間の目安

健全な構築済み環境、利用可能なモデル容量、既存のローカル依存、サインイン・秘密入力の準備がある場合の概算。実行時間の保証ではない。

| 工程 | 概算 |
| --- | --- |
| 共通確認・変更候補・ローカル異常系のまとめ確認 | 15～25分 |
| Foundry容量変更と設定の同期、正常候補G→Pの反映・確認 | 35～50分 |
| 旧容量・定義・Portalへの復旧、G→Pの反映と最終確認 | 25～40分 |
| 運用テスト本体 | 約1.5～2時間 |

初期構築を必要とする場合は別途約1.5～2時間、環境全体の撤去まで行う場合は約45～90分を見込む。再構築・運用テスト・撤去を含めた作業枠は約4～6時間。大きな不具合改修、サインイン待ち、利用枠不足、Azure側の長い更新待ちを通常の試験時間へ埋め込まない。発生時は状況と延伸見込みを報告する。

## 判定と記録

結果は未実施／実施中／PASS／FAIL／ブロック／合意した対象外を使う。机上確認は手順・実装・CLI引数・ローカル回帰の整合確認であり、実配備や実測のPASSを意味しない。本仕様の12件は実施前のため全件未実施である。

異常系3件は、表に指定した隔離入力・ローカル検査で判定する。`OPS-MODEL-02`は`tests/test_publish_apis.py`の`PublicationTests.test_model_deployment_and_scoped_role_prerequisites_are_checked_before_firewall_changes`など、偽のモデル読取結果を用いる制御試験で確認する。Gの`--execute`は実モデルの前提検査までにBroker・SQL等も配備するため、不一致入力を渡して「全Azure書込0」の試験にしない。正常反映・切戻しを期待する行は、実際の反映値・動作まで確認する。

実施票は`ID / revision / 対象参照 / 変更前後 / 刺激・期待 / 実結果 / 終了コード / 復旧・回収 / 判定・残件`を持つ。実測値を含む票と必要最小限のテキスト証跡は`.local/<environment>/evidence/<run-id>/`へ保護保存する。キー・token・Cookie・秘密値を通常ログへ出さず、大きなログの一括取得や画像・動画の追加採取は行わない。
