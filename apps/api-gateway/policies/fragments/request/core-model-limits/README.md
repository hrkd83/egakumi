# 本文サイズの確認

選択済みの操作・モデル設定に従い、受信した本文サイズを確認する部品です。Azureのフラグメント名・フォルダ名・XML・C#の名前を`core-model-limits`に揃えます。

同名XMLが外枠、同名C#が検査の本体です。既存の生成処理がC#と説明コメントをXMLへ展開し、Azureへ完成XMLを渡します。他のフラグメントのソースは、この部品へ展開しません。

## 呼び出しと入出力

HTTP APIテンプレートが、操作・モデル設定の準備と認証結果の引き渡しの後、本文の書き換えやバックエンド認証より前に呼びます。WebSocketやMCPの入口テンプレートからは直接呼びません。生成MCPから参照先REST APIを実行する場合は、そのHTTP側で処理します。

| 入力・出力 | 内容 |
| --- | --- |
| `gatewayOperationConstraint` | 先行処理が選んだ操作・モデル設定のJSON文字列 |
| `gatewayOperationSelection.requestBodyBytes` | モデル選択で本文を読んだ場合の測定バイト数。未測定ならこの項目はない |
| 要求本文・ヘッダー | 必要な検査で読む。本文は`preserveContent: true`で保持する |
| `gatewayLimitDecision` | `allowed`・`status`・`code`を持つ検査結果のJSON文字列 |

呼び出し元が結果を読み、停止する場合の監査記録とHTTP応答を行います。この部品は要求や応答の本文を監査へ記録せず、応答本文は読みません。

## 現在の処理

1. 内部設定JSONを取得・解析する。失敗時は500・`LIMITS_NOT_CONFIGURED`で停止する結果を返す。
2. 配備時に用意した`bodyFormat`が文字列で`json`・`binary`・`multipart`・`text`・`none`のいずれかかを確認する。欠落・不正値は本文を読まず500・`LIMITS_NOT_CONFIGURED`を返す。
3. `none`なら本文と`maxRequestBytes`を読まず成功する。これは、この部品で本文を検査しない指定であり、本文の存在禁止ではない。
4. 本文を扱う4形式だけ、`maxRequestBytes`を整数・1〜500 MiBの条件で一度だけ`long`へ変換し、検査で使い回す。変換できない値や桁あふれ・範囲外は500・`LIMITS_NOT_CONFIGURED`を返す。
5. `binary`・`multipart`・`text`は、読み取れた申告サイズを検査する。`requestBodySizeCheck`が未指定または`actual`なら、実受信サイズも確認する。`declared`ならこの部品で本文を読み出さず成功する。Content-Lengthの構文はHTTPの受信処理に任せ、この部品で形式不備を400にはしない。Content-Typeの許可一覧との比較は行わず、受付形式の判断は提供元に任せる。
6. `json`は、先行処理の測定バイト数があれば再利用し、なければ元の本文を読んでサイズを確認する。選択後の本文上限と比較する。汎用の出力トークン・整数・配列件数・文字列選択肢の検査は行わない。

この部品では本文をJSONとして解析せず、出力トークン・整数・配列件数・文字列選択肢・Embedding・Rerankの入力条件は提供元へ任せます。後段のJSON・モデル照合は別の処理として残ります。

PIIの受信サイズには、JSONエスケープを考慮する既存の6倍枠を使います。上限はAPIMの500 MiB以内とし、PII操作側で解析後のサイズを別に確認します。

## 棚卸の状態

冒頭の内部設定JSONの取得・解析が例外になった場合は、本文不備400から基盤側の500・`LIMITS_NOT_CONFIGURED`へ分けます。変数の欠落・null・文字列以外・不正JSON・JSONオブジェクト以外を、この読取り失敗として扱います。

本文を扱う4形式では、上限設定の整数・1〜500 MiBの条件を維持し、数値への変換を一度にまとめます。桁あふれを例外400にせず、設定不備500へ揃えます。先行処理はモデル選択前の操作共通上限を確認するため、選択後の上限や、先行処理が本文を読まない操作の設定確認はこの部品で維持します。

本文形式の補完は正式な配備手順の正規化処理へ統一します。標準・追加APIとも、明示された形式を優先し、未指定なら操作に応じて`json`または`none`を補います。この部品は実行時にJSONへ読み替えず、内部設定の文字列型と5形式を一度だけ確認します。クライアントのContent-Typeはこの判定に使いません。

`none`は内部JSONと本文形式の確認後、上限確認より前に成功を返します。使わない上限が欠落・不正でも、この部品では要求を止めません。配備前の上限設定検査は維持します。

`binary`・`multipart`・`text`のMIME許可一覧比較と、それによる415を撤去します。提供元が対応していても基盤の一覧更新漏れで止まることを避け、サイズ検査を維持します。前段のContent-Typeヘッダー検査の対象は増やしません。

`contentTypes`設定は、API定義の生成・SpeechのSSML検査対象の選択などにも使うため残します。Documentの個別形式検査は、[専用入力部品](../core-document-input-validation/README.md)の棚卸で撤去します。SpeechのWAVヘッダー上書き、WAFの形式制御は続く棚卸の対象です。この比較の撤去だけで、任意形式が経路全体を通るとは扱いません。

Content-Lengthを数値化できない、または負数の場合に、この部品で400にする処理は撤去します。ヘッダーによる本文の区切り・構文の扱いはHTTPの受信処理に任せます。読み取れた申告サイズによる早期413を維持し、ヘッダー省略も認めます。実受信サイズを確認するかは操作設定で指定します。ポリシー式のローカル試験は、HTTP受信層が不正な要求をどう扱うかの確認とは区別します。

申告サイズから上限超過が分かる場合の早期413は、不要な本文読取りと後続処理を省くため維持します。この部品の`As<byte[]>`による読取り前に停止する処理であり、AppGWやAPIMが先に行った受信・保持処理まで省ける保証はありません。省略・数値化できない値・上限以下は、操作設定に従って実受信サイズの検査か、本文を読み出さない成功へ進みます。

## 非JSON操作の本文サイズ確認

操作の基本設定に、汎用の`requestBodySizeCheck`を指定します。API名・操作名をC#へ固定せず、同じ方式の操作を設定だけで追加できます。配備前に値と対象形式を確認し、`binary`・`multipart`・`text`で使います。

| 設定 | この部品での処理 | 成功時のcode |
| --- | --- | --- |
| 未指定／`actual` | 読み取れた申告サイズに加え、本文をバイト配列へ読み出して実サイズを比較する。元の本文は保持する | `BOUNDED_UPLOAD` |
| `declared` | 読み取れた申告サイズだけを比較し、本文を読み出さず後続へ渡す | `DECLARED_SIZE_ONLY` |

標準の音声認識（Speech STT）・音声ファイルの文字起こし・画像編集・音声合成（Speech TTS）・Document解析の5操作を`declared`にします。TTS以外の4操作は後段で本文を読む必要がなく、サイズ検査だけの全量読取りを省きます。Content-Lengthが省略されるなど比較できない場合は、この共有部品による実サイズの413もありません。この4操作の受付サイズは提供元が判断し、Azure自身の技術制約は別に扱います。

TTSの実サイズ検査は、直後の[core-speech-ssml-guard](../core-speech-ssml-guard/README.md)へ集約します。本文を一度読み、選択済みの上限との実サイズ比較を文字列化前に行い、同じ本文で既存の宣言検査を続けます。申告による早期413はこの共有部品に残し、実サイズ超過の413とSSML拒否の400は、利用枠・下流認証準備・`accepted`監査より前でAPIが監査・応答します。

Document解析は`declared`へ整理し、共有／個別のサイズ確認だけの全量読取りを撤去します。申告サイズの500,000,000 bytes枠は、原本と提供元JSONの送信本文全体へ適用します。Base64の復号後やURL先の文書サイズは提供元が判定し、APIMでは計測しません。このDocument入力ブロックはAzure反映・読戻し照合を完了し、独立して作成した小文書の原本・Base64入力はキー／Bearerで202受付から本文なしGETの200まで一部確認しました。申告サイズ境界・内部障害500・期限切れ410など残る受入は未実施です。JSONなどの未棚卸処理は変更しません。TTSでは全文の文字列化・小文字化が残り、共有テンプレートにもほかの本文読取りがあるため、今回の変更だけで完全な無バッファ転送が実現したとは扱いません。

## JSON本文の測定値の再利用

モデル選択が本文を読んだ場合、その成功結果の`requestBodyBytes`を元本文の測定値として使います。先行処理からこの比較まで本文の書き換えがないため、サイズ確認のためだけの二度目の全量読取りを省きます。選択後のモデル上限との比較と超過時の413は維持します。標準ではOpenAI Chat／ResponsesとFLUX生成／編集の4操作がこの方式を使い、追加APIも同じ先行処理で測定していれば再利用できます。

測定値を渡さない操作は、この部品で従来どおり本文を読みます。PIIのJSONエスケープを考慮した6倍の受信枠も維持します。`none`・非JSON形式は先に処理を終えるため、この内部結果を読みません。内部結果を取得・解析できない場合は500・`LIMITS_NOT_CONFIGURED`を返します。測定済み整数の網羅的な再検査は追加せず、サイズ比較を本文のJSON解析と切り離します。後段のJSON・モデル照合に必要な本文解析は維持します。

この整理はローカル実装と実C#式の試験を完了し、再読取り削減・元本文保持・選択後上限413・未測定時の読取り・PII受信枠を確認しました。Azure反映・読戻し・実接続の確認は、次の変更ブロックをまとめて行います。
